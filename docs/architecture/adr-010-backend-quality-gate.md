# ADR-010: Backend Quality Gate

**Status**: Proposed  
**Date**: 2026-06-18  
**Author**: FAANg Tech Lead (Sisyphus)  
**Deciders**: FAANg FAANg Agents (Tech Lead, Principal Architect, QA Engineer)  

## Context

The CloudBuilder backend has 44 service classes across 18 modules, but only 9 JUnit test files covering approximately 12 services. This means ~73% of services have zero test coverage. As the codebase grows, untested services will accumulate technical debt, making refactoring risky and regression detection impossible.

Key metrics:
- **44** total service classes
- **9** existing test files (99 tests passing)
- **32+** services without any tests
- **18** main packages, only **8** have any test coverage
- **3 modules with partial coverage** (design, provision, platform, aiops)
- **9 modules with zero coverage** (audit, codeanalysis, docs, git, github, metrics, multiregion, observability, tenant)

Without systematic test coverage, we cannot:
- Safely refactor core services
- Detect regressions during feature development
- Validate edge cases in complex logic (e.g., code generation, drift detection)
- Achieve production readiness for enterprise customers

## Decision

We will implement a **Backend Quality Gate** with the following elements:

### 1. Test Coverage Standards

| Tier | Criteria | Target |
|------|----------|--------|
| Gold | All services tested | ≥80% service-level coverage |
| Silver | Core services tested | ≥60% service-level coverage |
| Bronze | Critical paths tested | ≥40% service-level coverage |

**Phase 5 target**: Silver tier (60%+ service coverage) — every module has at least basic tests for each service class.

### 2. Service Test Pattern

All new service tests follow the established `CostServiceTest` pattern:

```java
@ExtendWith(MockitoExtension.class)
class XxxServiceTest {

    @Mock
    private XxxRepository xxxRepository;

    private XxxService xxxService;

    @BeforeEach
    void setUp() {
        xxxService = new XxxService(xxxRepository);
    }

    @Test
    void methodName_ShouldExpectedBehavior() {
        // Arrange
        // Act
        // Assert
        // Verify
    }
}
```

**Rules**:
- Pure **Mockito unit tests** — no Spring context loading
- Constructor injection only (matching production code pattern)
- One `@BeforeEach` setUp method instantiating the service
- Every public method gets at least one test covering happy path + edge cases
- Business logic branches get parameterized tests where appropriate
- Repository calls verified with `verify()` to ensure correct port interaction

### 3. Methodology

Tests will be generated by FAANg agents following this pipeline:
1. **Read** service source → understand constructor deps, method contracts, port interfaces
2. **Mock** all repository/port dependencies
3. **Test** each public method: happy path, null/empty edge cases, boundary conditions
4. **Verify** with `verify()` that correct port methods are called with correct args
5. **Compile-check** with `mvn compile test-compile` before finalizing

### 4. Phased Rollout

| Phase | Scope | Services | Target |
|-------|-------|----------|--------|
| 5a | Core untested | audit, docs, tenant, codeanalysis | 4 services |
| 5b | Observability + MultiRegion | observability (7), multiregion (4) | 11 services |
| 5c | Remaining uncovered | Git (2), GitHub (1), Metrics (1), design-remaining (3), provision-remaining (7), platform-remaining (1), aiops-remaining (2) | 17 services |
| 5d | ID type consistency | Frontend nanoid ↔ Backend UUID mapping | Across stack |

### 5. Verification Gate

After each phase:
```bash
mvn compile test-compile  # Must pass with zero errors
mvn test                  # All 99+ existing tests must still pass
```

New tests failing → agent must fix before proceeding.

## Consequences

**Positive**:
- Every backend module gets baseline test coverage
- Regression detection for all existing service methods
- Established pattern makes future test creation mechanical
- Documentation of service contracts through test assertions

**Negative**:
- ~20 person-days of test creation work (delegated to FAANg agents)
- Mock tests don't catch integration issues (reserved for Phase 6 Testcontainers)
- Some complex services (DocScannerService, CodeAnalyzerService) require careful mock setup

**Neutral**:
- New services must include tests as part of implementation going forward
- CI pipeline will enforce test compilation going forward

## Alternatives Considered

1. **Testcontainers integration tests** — More realistic but much slower to run and harder to maintain. Deferred to Phase 6.
2. **ArchUnit tests** — Good for architecture enforcement but doesn't cover business logic. Could add in later phase.
3. **Only test new code** — Leaves existing untested code fragile. Rejected.
4. **Skip testing, focus on features** — Pragmatic short-term but accumulates critical debt. Rejected.

## Future Work (Phase 6+)

- Integration tests with Testcontainers (PostgreSQL, Kafka, Redis)
- ArchUnit tests for hexagonal architecture enforcement
- Mutation testing (Pitest) for test quality measurement
- Contract tests (Pact) for cross-module boundaries
